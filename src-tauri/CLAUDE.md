# ProjectEldrun — Backend File Map (`src-tauri/src/`)

See the root `CLAUDE.md` for project-wide context (running, persistence, dev
workflow); see `src/CLAUDE.md` for the frontend file map.

**Top level**

| File | Purpose |
|------|---------|
| `main.rs` | Tauri app entry point, plugin registration. |
| `lib.rs` | Command registration (`generate_handler!`), app setup, hook/restore install. |
| `storage.rs` | JSON persistence helpers (read/write state files). |
| `paths.rs` | Canonical Eldrun directory paths. |
| `sysstat.rs` | Per-process CPU sampling via `/proc` (`descendant_pids`), the whole-system `SystemSnapshot` behind the monitor pane, and `machine_load()` — the **aggregate-only** sample (CPU times, memory/swap, load, CPU temp) with *no* process table. That third one exists because a process walk is the expensive half: the 🧠 local-model menu polls "how loaded is this machine, and what is left for the next model" every couple of seconds while hovered, and paying a `/proc` read per process (plus the JSON for all of them) for a figure it never shows is a price only the pane's own view justifies. Each platform backend implements it beside its `system_snapshot` from the same primitives, so the two can't disagree; a target with no backend answers `supported: false` rather than zeros. |
| `gpustat.rs` | Whole-**device** GPU memory (the header row, the monitor pane, the model menu's headroom line) — Ollama's `/api/ps` figure is now one line of its breakdown, not the reading. Reports a GPU's **two** pools separately because on an APU only one is real: the dedicated VRAM carve-out (~512 MB — the framebuffer, permanently ~full, so it alone says nothing) and the shared pool mapped out of system RAM (amdgpu's GTT, where a model actually lands); callers sum them, and on a discrete card the shared half is 0 so the sum collapses to plain VRAM. Sources: **DRM sysfs** (`mem_info_*` + `gpu_busy_percent` — no tool, no root) and **`nvidia-smi`** (the only portable NVIDIA read; a process spawn, so its *absence* is remembered rather than re-paid every poll). A card is only reported when it states a `vram_total` — Intel's `i915` exposes none, and a zero is not a measurement. One ~1 s cache serves all three surfaces. Each `GpuSample` also carries the card's **sensors** — temperature, power (draw + cap), core/mem clocks, fan %, PCIe link, driver version — read from the *same* cheap sysfs (a card's `hwmon` subdir + `pp_dpm_*`/`current_link_*`) / `nvidia-smi` pass, so every surface gets them free; each is `None` when the driver won't say (never a fake zero). **Per-process** GPU memory is deliberately separate (`process_snapshot` → `gpu_process_snapshot`, monitor pane only, *not* cached into the shared snapshot): a heavier read (a `/proc` `fdinfo` walk deduped by `drm-client-id` for amdgpu, an `nvidia-smi --query-compute-apps` spawn) the always-visible header must not pay for. A **remote** project samples its host's GPUs too: `sysstat::REMOTE_SNAPSHOT_SCRIPT` ships the host's DRM sysfs files (`AMD\t…` lines) and raw `nvidia-smi` CSV (`NVSMI`/`NVPROC`) over the one SSH round-trip, and `parse_remote_snapshot` runs them through these *same* `parse_drm_card`/`parse_nvidia_smi`/`parse_nvidia_apps` parsers — so a host GPU reads field-for-field like a local one. Remote per-process is NVIDIA-only (the AMD `fdinfo` walk is too heavy to run per remote poll). |

**Commands (`commands/`)** — Tauri command handlers exposed to the frontend.

| File | Purpose |
|------|---------|
| `projects.rs` | Project CRUD, scaffold/import, time-today (god module; #1). Also the **duplicate gate** (#152): `find_project_conflict` is the one answer to "is this already a project", asked by `create_project`, `import_project`, `finish_import` and `extend_project_to_remote` so four call sites cannot drift into four definitions. It compares a `ProjectSite`, not a path string, and the distinction is the whole point — a *local* project is its directory (canonicalized, so a trailing slash or a symlink cannot smuggle a second registration past it), a *remote* one is its SSH target + host path, because its registered `directory` is a per-id state dir that never matches twice however often the same host folder is imported. A remote project's **mirror** counts as an owned tree too. `import_project` runs it **before** the mode dispatch moves anything: the check used to see only the destination, so a `move` re-import under a new name moved the tree out from under the original entry. `copy` is deliberately exempt (new directory, source left registered and intact). `check_project_site` is the same resolver as a read-only query, so the dialog can warn — and offer to open the existing project — before a clone downloads a repo that would be refused. |
| `fs.rs` | File-I/O commands (read/write/mtime, extracted from `projects.rs`; #1 seam). |
| `fs_watch.rs` | Filesystem watch start/stop + change events. |
| `git.rs` | Git status/history/commit/push. Also the **worktree** surface (#23, `docs/worktree_improvement_plan.md`), whose three non-obvious rules are all about the fact that the git verb is the easy part. **Where the operation runs is not where the bytes the user picked live**: for a remote project `project_dir` is the *local mirror*, so resolving remoteness from it alone created host worktrees at mirror-shaped paths and left the mirror's own repo unmanageable — `WorktreeSite` makes the choice explicit, following `git_publish`'s `PublishSite`. **A worktree has exactly one legitimate home**: `git worktree add <path>` creates *and populates* `<path>`, i.e. an unconstrained path argument is a "write repo-controlled content anywhere writable" primitive, including somewhere Eldrun later reads back as intent (#151) — so `resolve_worktree_path` confines every one to `<root>/.eldrun/worktrees/`, which also makes it invisible to both byte-sync walkers and *visible* inside the container (the linked `.git` file's `gitdir:` pointer resolves, because the project dir is mounted at its identical absolute path). **`worktree add` checks out, and a checkout runs hooks**: `NO_HOOKS_CONFIG` (`-c core.hooksPath=`) is pinned on these verbs and on `git_checkout`, deliberately *not* in `HARDENED_CONFIG`, which `git_commit` also goes through and where the user's own hooks are the point. `force` on remove is a **count**, not a flag — git answers a locked worktree with "use 'remove -f -f'" and exits 128 for a single `--force`. |
| `git_publish.rs` | Publish a project's repo to GitHub (`gh`) or GitLab (`glab`). Owns the shared `Provider` (which CLI, which token/host env). Also owns **which side runs the CLI** (`PublishSite`), which is the one non-obvious thing here: *where the bytes are is not where the hosting account is*. `gh auth login` and the Settings → Git Hosting tokens are secrets of the local machine, while a work remote is typically a cluster login node with no provider CLI, no GitHub credentials and often no outbound https — so a remote project publishes **from its lockstep mirror by default** (`publish_from = "local"`, the dialog's "Publish from" selector), and the ssh path is the explicit opt-in for a host with its own login. The local default's one hazard is a stale mirror, so `describe_mirror_guard` (pure, tested) refuses unless lockstep is enabled *and* green — otherwise a publish would create the repo from the wrong history. Every follow-up (visibility, unpublish, and `commands::git::git_push` via `mirror_origin_repo`) routes by `origin_site`: wherever `origin` actually got wired, so the create and the pushes never end up on opposite sides. `run_remote_provider_command` additionally translates OpenSSH's own failures (`ssh_transport_error`) — `ssh_base_args` reuses but never creates a master, so a disconnected project fails at ssh auth, and "Permission denied (publickey,password)" reads like a GitHub rejection if passed through raw. |
| `git_fork.rs` | The import dialog's **fork** source: fork a hosted repo into the user's own account, then clone *that*. A fork is a server-side operation, so it goes through the provider CLI's raw `api` subcommand (`gh api -X POST repos/<owner>/<repo>/forks`, `glab api -X POST projects/<id>/fork`) rather than `repo fork --clone` — the response JSON *names* the fork, and neither CLI's clone can be pointed at a destination directory or have its namespace guessed (a fork can land elsewhere, or already exist: GitHub returns the existing one, GitLab refuses with "already been taken", which is looked up instead of reported). The clone itself is `git::git_clone_blocking`, so the URL whitelist, token credential helper and partial-directory cleanup are the ordinary clone's; it is retried only on the "not there yet" failure, since forking is asynchronous on both services. `git remote add upstream <original>` is best-effort — the tree is on disk by then. `fork_cli_available` backs the dialog's install banner. |
| `terminal.rs` | Terminal/PTY command surface (delegates to `terminal/mod.rs`). Also the **local** tmux-session commands (TODO #85): `local_tmux_{list,kill,rename}`, and the `pty_spawn` local-tmux wrap (`services::tmux_local`). |
| `apps.rs` | App launching, `run_script_detached`, `open_file`, external window tracking. |
| `default_apps.rs` | Per-file-type default-app mapping. |
| `downloads.rs` | Per-project download routing. |
| `ssh.rs` | SSH commands for remote projects (`ssh_connect`, `ssh_default_dir`, `ssh_list_dir`, `ssh_tooling_status`). Also the **active-disconnect** pair (explicit-click only, never on relaunch): `remote_kill_all_jobs` (`tmux kill-server` on a host — ends *every* running session/job, best-effort, rides a live master or authenticates ad-hoc like `global_machine_monitor_snapshot`) and `ssh_close_master` (`ssh -O exit` on the shared `cm-%C` socket, for a project-free global machine that pools nothing; a project host tears its pool down via `remote_disconnect` instead). |
| `remote.rs` | Pooled SSH/SFTP connection lifecycle (`remote_connect`/`remote_disconnect`) for the active remote project. Also `remote_upload_file` (HPC wizard "Load data" step, `docs/quirky-knitting-umbrella`): streams a local file to `<remote_path>/<dest_rel>` over the pooled SFTP (`upload_file_streaming_on`), primary host, dest_rel sanitized to stay inside the root. Also the tmux-session commands (TODO #85): `remote_tmux_list` (Sessions view, `tmux ls` → `Vec<TmuxSession>`; called per-host so the view aggregates every connected worker), `remote_tmux_kill` (explicit-close / per-row kill), and `remote_tmux_rename` (per-row rename), all over the pooled ControlMaster. |
| `openvpn.rs` | OpenVPN tunnel connect/store-config commands. |
| `ollama.rs` | Ollama model list/pull/delete + local autocomplete. **Where the server is** is `resolve_ollama_addr` (pure, tested) and nowhere else: `Settings::ollama_host` was declared for years and read by nothing while the transport dialled a literal `127.0.0.1:11434`, so anyone running Ollama on another port had a setting that did nothing (#201a). It is read per call — a settings write is not an event this module hears — and three of its rules are the point rather than plumbing. **`https://` is an error, never a downgrade**: this transport is a raw `TcpStream` speaking HTTP/1.0, and connecting in the clear to an address the user wrote as TLS would put their prompts on the wire while the setting says otherwise. **A non-loopback host needs `ollama_allow_remote_host`** (default false, a second key because it is a second decision — another *port* is still local inference, another *host* means every prompt and every file an agent reads leaves this machine), judged on the literal typed and never on what it resolves to. And the connect is **bounded** (4 s), which only became necessary once a remote host was reachable at all: a bare connect at a host that is off or mistyped blocks on the kernel's TCP retries for minutes, the window-freeze shape this repo has paid for before; loopback refuses instantly and never reaches the bound. `ensure_ollama_running` inherits the consequence — it refuses a remote endpoint by name rather than silently spawning a *local* server the caller was never pointed at, tries the systemd unit only for the default address (the unit binds what the unit says), and hands a spawned `ollama serve` an `OLLAMA_HOST` so a non-default port is bound rather than waited for in vain. `ollama --version` is deliberately **exempt**: it reads the installed binary's version, which is what the `launch` feature gate is about, and pointing it at the host costs both the documented "touches no network" property and two minutes against an unreachable one. Also the three things that have to be asked about rather than assumed — two about a *model*, one about the *machine*. **The GPU**: Ollama ≥0.32 **drops integrated GPUs by default**, logging "dropping integrated GPU; to enable, set `OLLAMA_IGPU_ENABLE=1`" and then naming `cpu` as its only inference device — so on a machine whose sole GPU is the APU, an ordinary update moves every model onto the CPU and the only trace in the API is a `size_vram` of 0, which is *also* exactly what a model too large to fit looks like. Three answers, and the split between them is the point. `ensure_ollama_running` sets the variable on the server **Eldrun itself** spawns (ours to configure; an explicit value already in the environment is left alone, because a user who set `0` meant it), which reaches nothing about a systemd-managed one. `LoadDevice` (`auto`/`gpu`/`cpu`) is the per-load choice, mapping onto the one option llama.cpp exposes for this — `num_gpu` omitted / `MAX_GPU_LAYERS` / `0` — and `auto` is a real third value rather than the absence of a choice: deferring to a scheduler that knows what else is resident is not the same act as overriding it, which is also why `Auto` omits the option instead of computing a number with strictly less information than the scheduler has. And `ollama_gpu_status` is the diagnosis, which exists because `size_vram: 0` alone cannot support one: it sets `igpu_dropped` only when **four** facts line up (a resident model with nothing on the GPU, a GPU that exists, *every* GPU here integrated, and the installed server still offering the flag — read from its own `ollama serve --help` rather than guessed from a version number, so it stays right across an upgrade mid-session), because blaming a setting for an ordinary out-of-VRAM would send the user off to reconfigure a system service for nothing. Its `fix_cmd` is a systemd **drop-in** (additive, survives the installer rewriting `ollama.service`, undone by deleting one file) handed to a terminal for the user to run rather than applied silently — it needs a root password, and a command that reconfigures a system service is one they are entitled to read first. A `gpu` load is a **request, not a guarantee**, and the two halves are why: the option can only distribute layers across the devices Ollama registered *at startup*, so a server that dropped the GPU at discovery has nothing to offload to and the load still lands on the CPU. **Capabilities**: `OllamaModelInfo` carries Ollama's own list (`/api/show`), cached against the **manifest digest** rather than the name — capabilities are a property of the manifest, so a digest read once can never need re-reading and a re-pull misses the cache by construction, which is what keeps the 🧠 menu's every-hover list from paying a round trip per model. The rule every consumer honours is that **an empty list means "could not ask", never "supports nothing"** (`model_capabilities` deliberately does not cache a failure), because the alternative is a timed-out probe silently emptying a menu. That feeds the **tool gate**: every `LOCAL_DRIVERS` entry is a tool-calling agent, so `list_local_drivers` takes the active model and withholds them from one that positively lacks `tools` — otherwise Codex-on-`deepcoder` opens a tab that dies on its first request with a raw `does not support tools` JSON error. `prepare_local_launch` refuses again (the menu is a cache; the active model changes under it) and names the models on *this machine* that would work, since a hardcoded example list would age. `driver_verdict` is the pure, tested core of both. `thinking` is the **second** capability a model can refuse and it behaves oppositely, which is the distinction worth keeping: a model without it does not merely skip reasoning — Ollama rejects the *whole request* with `"<model>" does not support thinking` — but the agent is fine, it just must not ask, so the answer changes the launch line instead of withholding the agent. Only Codex needs it (`model_reasoning_effort` defaults to `medium`, and the user's own `~/.codex/config.toml` usually sets it outright), and `qwen3-coder` is exactly the shape that made it a bug rather than a theory: it reports `tools`, so it sailed through the tool gate and died on its first turn. The load-bearing consequence is that `non_thinking_args` also means **bypass `ollama launch`** — `launch` forwards nothing to the agent (an extra flag is an `unknown shorthand flag` error) and its generated `~/.codex/model.json` + profile do not turn reasoning off — so the direct `codex --oss` invocation is the only working path for such a model, not a downgrade. That fallback also names `oss_provider` via `-c` rather than the `--local-provider` flag Codex's error suggests: an unknown *config key* is ignored by an older Codex, an unknown *flag* is a hard argv error. `non_thinking_override` is the pure core, and "could not tell" leaves reasoning on, matching the tool gate. Bypassing `launch` costs the *other* thing it was doing, which is why `wants_local_catalog` exists: `ollama launch` generates a Codex model catalog (`~/.codex/model.json`) and points the agent at it, and without one Codex says `Model metadata for '<model>' not found` and then reasons about the context window from a built-in guess — it does not know `qwen3-coder` holds 262 144 tokens, so it compacts against the wrong number, either discarding context that still fit or overrunning a window whose truncation Ollama does not report back. `write_local_catalog` writes the same document into **Eldrun's own** state dir (`codex_local/<alias>/model.json`) rather than `~/.codex`, which is another application's to manage, and reads the two model-dependent facts off `/api/show` instead of assuming them — the context window (found by `.context_length` *suffix*, since the key is architecture-prefixed, so a new model family needs no table entry) and whether any reasoning level may be offered. An unknown window is **omitted**, never defaulted: a wrong one is worse than the fallback because it is wrong with confidence. The write is best-effort — a catalog that could not be written costs a warning, and must never become a refusal to open the tab. `local_catalog_json` is pure and tested. **Update checks**: Ollama has no "is there a newer version" API — a pull just re-resolves the tag — so `ollama_check_updates` compares the digest `/api/tags` reports against the `ollama-content-digest` header the registry answers for the same `name:tag`, one HEAD per model through the same `curl` transport `fetch_registry_manifest` uses. It is **on demand only** (a button in the 🧠 menu, never a hover/timer/launch sweep), and a model the registry could not be reached for comes back with `error` set and `update_available: false` rather than dropped — "couldn't tell" must not render as "up to date". `ollama_version_status(check_remote)` is the same question about the **server itself**, and it is a separate surface because it is a different kind of fact: a server a few minor versions back is missing whole *features* rather than weights — `ollama launch` (the only wiring that stands up an Anthropic-compatible endpoint for Claude Code) does not exist before v0.15, so on an older server that agent is absent from the + menu with nothing saying why. The split is the point: `check_remote: false` is a local `ollama --version` and touches no network, so the menu can show what is installed on every open, while the newest published version costs one unauthenticated GitHub request and rides the same click. `version_is_newer` compares **numerically**, which is the whole reason it exists rather than a `<` on the strings — `"0.9.0" > "0.14.3"` as text, so a lexical compare would have announced a downgrade as an update for most of Ollama's history — and answers `None` for anything unparseable, which is reported as "couldn't tell" and never as an update. `parse_version` scans for a version-shaped token instead of taking a fixed field, because the command prefixes a warning line whenever the server isn't running. All of it is reproducible headlessly via `examples/ollama_probe.rs` (`cargo run --example ollama_probe`) — these are ordinary `async fn`s under an attribute, so awaiting them needs no window and no click, which is the only way to tell "the button is dead" apart from "it ran and had nothing to report". |
| `tex.rs` | TeX compile + SyncTeX (shell-escape defense). `compile_tex` is **async** (`spawn_blocking`): a sync command runs on the main thread, so every TeX-figure add and every Recompile used to freeze the whole webview for up to the 600 s run timeout. Also home to two commands the deck presenter needs. **`synctex_page_lines`** reads the `.synctex.gz` a compile already emits (`-synctex=1` is passed unconditionally) and reports the source lines behind each PDF page — the *producer* half of a deck slide's line anchor, which `sidecar.ts` documented and consumed but nothing ever wrote, so the mechanism did not exist at runtime. It parses the file rather than shelling out to `synctex edit` per page (a 200-page plate would be 200 process spawns for one reconcile), and harvests only the **main input's** tag, because line numbers from two files are not comparable and mixing them would be an anchor that silently means nothing. **`list_fonts`** walks the platform font directories for formats fontkit can embed, returning **paths** — the frontend measures and embeds by path, since two files can claim one family name and the export would otherwise be a coin flip. |
| `boxes.rs` | Project-box CRUD. |
| `browser.rs` | **In-app browser** (TODO J #61, `docs/browser_plan_{a,b,c}.md`). Two surfaces, deliberately *neither* an embedded pane: an in-pane **reader** tab whose page is fetched and sanitized in Rust (`browser_reader_fetch` → the mail client's own `ammonia` pipeline → inert HTML in a `sandbox=""` srcdoc frame, so **no JavaScript ever runs**), and a separate hardened **live-page window** (`browser_open_live`). An embedded child webview was ruled out because it does not work: `tauri-runtime-wry` packs one into the window's `GtkBox`, where `set_bounds` is a no-op, so N webviews stack vertically. The command surface is path-free, enforced the same way `mail.rs` enforces it (`no_command_takes_a_path` reads this file's own source) — with **one** documented exception, `url`, safe only because every one goes through `web_safety::navigation_decision` first and that gate hard-blocks `file:`/`tauri:`/`asset:`/`ipc:`/`javascript:`/`data:`/`blob:`. The live window is `incognito(true)` (ephemeral profile; nothing on disk, so quitting *is* the delete), `browser_extensions_enabled(false)`, `on_new_window` → `Deny` (a popup would be a chromeless window with no address bar), and `on_download` installed — wry's DEFAULT download handler allows *every* download to a path the page chose. Downloads land in `<state_dir>/browser/quarantine/` (0700, file 0600, exec bits stripped, never a project tree) and reach disk only via the native save dialog raised from Rust; `browser_download_decide` returns a **display name, never a path**. **Two gates, deliberately separate.** `LIVE_SUPPORTED` is false on Windows (WebView2's default permission state draws *Edge's own* prompt, whose Allow grants a browsed page the camera) — same posture as `services::sandbox` #86; `READER_SUPPORTED` is true everywhere, because that refusal is entirely about a *webview's* permission model and reader mode has none. They were one constant, which is how the Windows refusal silently spread to a surface its reason does not apply to. On top of the platform gate the live window needs `Settings::browser_live_pages`, **default off and off in debug too** (not an `experimental()` flag): two of its holes cannot be closed from app code, so it is opt-in rather than a line item inside `web_browser`. `browser_capabilities` folds both into one bool — the frontend's only question is whether to offer the control — and `browser_open_live` re-reads the setting rather than trusting that report. A tripwire suite scans the whole backend for the defences that would be silent if deleted: no certificate escape hatch, no permission/clipboard handler, no `register_uri_scheme_protocol` (every registered scheme is a *local* origin), no `ipc::Channel` (readable by any webview via the ACL-exempt `plugin:__TAURI_CHANNEL__|fetch`), no second keychain path, no foreign-browser-profile access. |
| `caldav.rs` | **CalDAV accounts** (`docs/caldav_plan.md`, `docs/context/caldav.md`) — the command surface, mirroring `mail.rs`'s account commands down to `{account, saved, save_error}`, with `caldav/accounts.json` behind them. A sync is deliberately **two** commands: `caldav_fetch` speaks the protocol and hands back each resource's iCalendar text *unparsed*, the frontend runs it through `src/lib/ics.ts` (the one parser here that understands folding/`RRULE`/`VALARM`), and `caldav_apply` reconciles the parsed rows through `commands::calendar::merge_caldav_calendar_at` in one atomic write — the same seam `calendar_fetch_ics` + `calendar_replace_events` already has, and for the same reason: a second iCalendar parser in Rust would be two implementations that can disagree about one feed. `caldav_fetch` does the cheap `getctag` check first (an unchanged collection costs one small `PROPFIND`, which is what makes a background timer affordable) and falls back from `sync-collection` to a full `calendar-query` whenever the token is unsupported or stale. The change tokens are written back **after** the merge succeeds and only then — a cursor saved over a failed write makes the next sync skip the very change it dropped. Credentials are not a fourth mechanism: `remote_credentials` keyed by *server target* (`caldav:<user>@<host>`), opt-in default off, `true \| null` never bare `false`. **Phase 3 (push)** adds `caldav_push`/`caldav_delete`/`caldav_resource_etag`/`caldav_refresh_access` on the same seam mirrored — `ics.ts` serializes the resource, these speak the protocol — and owns the part a serializer cannot know: **whether the write is allowed at all**. Three gates, none of them trusted to be the last one: `CalDavAccount.allow_write` (the user's opt-in, **default false** — the plan's "is write access even wanted against an institutional calendar?" asked rather than decided), `CalDavCalendarRef.read_only` (the server's own `current-user-privilege-set`, per collection), and the server's `403`. `writable()` is one function rather than a check per call site, because two sites checking "may I write here" separately is how one of them ends up checking half of it. A **delete is server-then-local** and the local row is the caller's to remove afterwards: the other order loses the row whenever the server refuses. A `412` comes back as `CalDavWrite.conflict`, a *value* the frontend renders a choice from, never an error string one surface pattern-matches. |
| `calendar.rs` | Calendar/event/task CRUD over `calendar.json` + guarded ICS file read/write. Also **`merge_caldav_calendar_at`**, the CalDAV reconciliation and the one genuinely new piece of logic that feature needs: `replace_calendar_events_at` re-mints ids on every refresh, which is fine for a manual click on an anonymous feed and catastrophic for an unattended timer — it would evict every CalDAV-sourced card from the to-do column the user dragged it into, every tick. A CalDAV resource carries a URL the server hands back unchanged, so rows are matched on `caldav_href` and merged field by field: the server's fields are overwritten, a task's `column`/`rank`/`tags`/`subtasks`/`mail`/`event`/`project_id`/`created` are not. Deletion is where the judgement is: an explicit `404` removes either kind; absence from a **full** listing removes an event but never a task (a VTODO can vanish because the server filtered completed ones, and that is indistinguishable from a delete); absence from an **incremental** report removes nothing (unchanged resources simply are not in it). Rows are matched *within* an href group, positionally, because one resource can hold a recurring master plus its `RECURRENCE-ID` overrides. Also the **to-do board's** two commands, and they are the only two the board needs — everything else (load, create/edit/delete a card, filters, convert-a-mail, both rails) reuses the existing task CRUD and `mail_priority_*`. `todo_move_tasks` applies a whole drag in ONE write: the frontend sends an **index**, never a rank, so the rank algebra (bisect, the too-close-to-split guard, the whole-column reindex to clean `RANK_GAP` multiples) lives in one tested place and a replayed placement is a no-op; it takes ids + target rather than a whole `CalendarData`, so a concurrent title edit in another window survives the same read-modify-write, and it **never refuses** a move for a WIP cap (a drag that reports success and snaps back is indistinguishable from a broken one). `todo_columns_set` is wholesale because a reorder is the common edit and a delete must refile its cards in the same write. Both call `ensure_board` — the board's columns are seeded by its first **write**, never by a read, which is what keeps a calendar-only user's file free of board state. Two long-standing bugs the board made load-bearing were fixed here: `create_task`/`update_task` returned the *pre-normalize* clone (so a new card came back with no column and did not render, and ticking in the Tasks view returned the stale column), and `write_data` truncated in place instead of using `write_json_atomic` — this file is now written on every drag, from a second window too. |
| `mail.rs` (priority marks) | `mail_priority_{set,page,counts}` — the **Important / Urgent** lists, and the only mail commands that touch **no network at all**. With no id configured the state is `Unconfigured` and **no verdict is shown at all** — a tick nobody checked is worse than no tick, since it teaches the user to trust something an attacker can draw. `apply_trust` is deliberately separate from parsing and runs on **every read**, so setting or clearing the id re-judges already-synced mail with no re-sync, and it *clears* `methods` outside `Verified` so stale data cannot leak through a future UI bug. Comments are stripped before anything is split — a real header carries `dkim=pass (1024-bit key; unprotected) header.d=…`, whose parenthesis holds both a `;` and an `=`, so not stripping first invents a clause boundary out of prose. Every clause keeps its `identifier` and an `aligned` flag against the visible `From`: `dkim=pass header.d=evil.example` on a mail claiming to be a bank is a *genuine* pass by the wrong signer, and that is the single most common misreading of these headers. The limit it cannot fix, stated in the module header rather than glossed: if your provider adds no header and an attacker forges one bearing its id, this believes it — RFC 8601 §5 puts the duty to strip forged instances on the MTA. |
| `mail_crypt.rs` | **The local mail store, encrypted at rest** (`docs/context/mail_encryption.md`) — the primitive and the key, and nothing else. One `ELMC` envelope shape (XChaCha20-Poly1305; the 192-bit nonce is drawn at random, so there is no counter to survive a crash *and* a restore-from-backup, which is how AES-GCM nonce reuse actually happens), HKDF subkeys off one master (`k_field`/`k_blob`/`k_addr`/`k_name`/`k_wrap` — compromise of one does not hand over the others), and a key file wrapping that master under either an OS-keychain KEK or an Argon2id passphrase (parameters recorded *in* the file, so they can be raised later without stranding a store). The load-bearing part is the **AAD**: every ciphertext is bound to `account‖table‖column‖row`, so an attacker with disk *write* access cannot relocate one message's sealed body onto another's row and have it render as that message — the class of attack at-rest encryption is famous for leaving open. `Unlock::Unavailable` is a **state, not an error**: a locked Secret Service collection reads identically to "nothing saved" and can block forever (the failure that once parked every connection lamp on amber), so the caller degrades to a memory-only store rather than making the mailbox unreadable. |
| `mail_crypto.rs` | The **format-agnostic seam** for end-to-end mail — what the *sender* did before the message left their machine, as opposed to `mail_crypt`'s at-rest job or `mail_authres`'s "what did my server conclude about the delivering hop". Detection is about **structure, not validity** (`CryptoKind` says what a message claims; whether it holds is a separate question), which is what let detection ship before verification without a half-built verifier being able to report a pass. Inline armor matches only at a line start, so a mailing-list thread *about* PGP does not grow a padlock, and a MIME wrapper outranks armor inside it (that armor is the ciphertext, not the message). **S/MIME is detected and not handled** — a recognized-but-unsupported format renders a banner; an unrecognized one renders its ASN.1 blob as though it were the mail. `info_for` is the single place the chrome rule lives: positive chrome needs a good signature **and** a key the user verified out of band **and** an identity matching the visible `From`; `Invalid` and `NoKey` are separate states, because "this is forged" and "I cannot tell" are different sentences. Every signed message carries a `headers-not-signed` note, because From/Subject/Date sit outside the signature in both formats and that is the thing users most reliably assume a tick covers. |
| `mail_filters.rs` | **The keyword matcher** — one pure question (does this rule match this header, and on which word?), with no I/O, no clock and no `AppHandle`, so "why was this marked?" and "why wasn't it?" are answered by a unit test rather than by a sync. Three rules carry it. **An empty rule matches nothing** — no terms, or no fields, fires on nothing and never on everything; both are one typo away in a dialog and the other reading empties the whole mailbox into the alert list on one tick. **Comparison is `to_lowercase`d**, not `eq_ignore_ascii_case`: these are ordinary words in whatever language the user writes their mail in, and `Rechnung` must match `RECHNUNG`. **The first matching rule wins, in list order**, because a message gets one mark and the order the user can see and drag is the only tie-break that can be explained. What it may look at is short and deliberate — subject, sender (address *and* display name, since a filter term is not an identity claim), recipients, and the body **snippet** the sync already stored, never the body: a sync fetches headers, so full-text matching would mean downloading every message of every folder on every check to decide a local column. `whole_word` is off by default and, when on, treats a term's own punctuation as its boundary, so `@acme.` still matches inside `@acme.example`. |
| `mail_engine.rs` | The mail protocol layer (MIME, IMAP, SMTP, TLS) — `AppHandle`-free and path-free, which is what makes plan A's landlocked-helper move a transport swap rather than a rewrite. Its module header owns the transport invariants (implicit TLS only, no certificate escape hatch, every network *and* parser bound). The one added since: **there is a session pool, and every IMAP operation leases from it** (#167). Each method used to log in, `SELECT`, run one command and log out, so reading twenty messages was twenty TLS handshakes and twenty `LOGIN`s — and the cost of that is not latency but the *provider's opinion of it*: hosted mail rate-limits authentication long before it rate-limits commands, and answers a client that reauthenticates per click with throttling, a lock, or a "suspicious sign-in" mail to the account being read. `set_flags_bulk` was already written against exactly that hazard; the pool generalizes it. Three rules carry it. `Lease.keep` is **false until `finish` is told the operation succeeded**, so an error, an early `?`, a panic or a future dropped mid-command by a cancelled sync all close the socket — the inverse default would hand the next caller a stream positioned inside somebody else's half-read response. A pooled session idle over 30 s is probed with `NOOP` (10 s cap) and one idle over 5 min is closed unread, because a pool with no liveness check has traded logins for intermittent failures. And `SELECT` is cached per session for the UID-addressed commands, but **`headers` always re-`SELECT`s**, since it reads `EXISTS` off the response and a cached count pages from a stale mailbox. `probe` is the deliberate exemption (`Acquire::Fresh`): a credential test answered out of a pool tests nothing. Callers evict on account upsert/delete and "forget password" — the moments a live authenticated socket stops matching the credential the user believes is in use. A tripwire test counts `imap_login` occurrences in this file's own source, so a method that starts logging in for itself fails rather than quietly reinstating the login storm. |
| `mail_pgp.rs` | The **OpenPGP keyring and the four operations** (rPGP; sequoia is LGPL and Nettle-by-default, which the no-C-toolchain invariant rules out). Sealed under `k_wrap` — deliberately not `k_field`, so the mail index and the private keys are not one compromise — and `open` takes `MailKeys`, so there is no unencrypted path by construction. **Key generation offers no algorithm choice**: `pgp` depends on `rsa` unconditionally and RUSTSEC-2023-0071 is unpatched, but the oracle is in RSA *decryption* and nobody can encrypt to a key we do not have, so Curve25519-only means that code is compiled in and never run for our mail (RSA stays importable — a correspondent's key is only ever used to verify). An imported key is `Known`, **never** `Verified`: OpenPGP has no CA, so only an explicit fingerprint comparison promotes it. `candidates_for` returns every key that *could* have signed, matching the primary **and every subkey** (signing is done by a subkey on every ordinary key, so matching the primary alone reports "no key" for keys we hold), and lets the cryptography pick — a 64-bit key id is short enough to collide on purpose. `signed_part_bytes` is the most dangerous function here and is commented as such: its failure is silent *and positive*, so it slices the **raw** message (RFC 3156 signs the part including its MIME headers, in transfer-encoded form) and drops the CRLF that introduces the closing boundary. `seal_outgoing` signs **inside** the encryption (the other order lets anyone strip and re-sign the ciphertext as their own) and has no path that returns plaintext on failure. |
| `web_safety.rs` | Shared web-safety primitives, extracted from `mail_sanitize` so the mail client and the browser cannot drift apart: `sanitize_attachment_name` (a message and a page pick filenames the same way), the host/scheme primitives (`scheme_of`/`host_of`/`idna_display`/`registrable`/`has_userinfo`), and the **navigation gate**. `mail_sanitize` re-exports the moved items, so every mail call site and its whole test table are untouched. The gate takes an already-parsed `Url`, never a `&str` — the entire `https://example.com@evil.example/` class exists because a display layer re-derived the host by string search. Three outcomes (Allow / Confirm / Block), an allowlist of `http`/`https`/`about:blank`/`about:srcdoc` plus an explicit deny list, and the **app-origin rule in BOTH build profiles**: Tauri's `is_local_url` calls the dev server (`http://localhost:1420`) and every `*.localhost` origin *local*, so a browser that reached one would clear the origin half of the ACL gate. `registrable()` stays the two-label approximation on purpose — moving it to a real PSL would change mail's cached mismatch decisions and needs its own `SANITIZER_VERSION` bump (so the address bar emphasizes the whole host, a documented+tested v1 limitation rather than a wrong guess). `REASON_TOKENS` is the **canonical list of every reason token a user can be shown**: the gate deliberately speaks in machine tokens so the wording can live in the frontend's i18n ×5, which is only safe because a Rust test proves the list covers every `BlockReason`/`ConfirmReason` variant and `src/__tests__/BrowserTripwire.test.ts` reads the list out of this file and fails if any entry has no phrase. |
| `window_service.rs` | Window-state helpers. |
| `skills.rs` | **Skills Library** (`docs/skills_plan.md`): fetch + catalog, no manifest, no versioning. A "source" is a git repo (`anthropics/skills` seeded by default), shallow-cloned/pulled into `~/.local/share/eldrun/skills_cache/<id>/` reusing `commands::git`'s hardened clone plumbing (`validate_clone_url`/`git_clone_blocking`, both `pub(crate)`) rather than adding an HTTP client. `list_catalog`/`get_skill_detail` walk the cache for `**/SKILL.md` and parse its YAML frontmatter (`name`+`description` only, via `serde_yaml`) fresh on every call — nothing about the catalog is persisted. `install_skill`/`uninstall_skill`/`list_installed` are a plain recursive copy/delete against a target's `.claude/skills/<name>/`; `list_installed` reads that directory directly, so a hand- or agent-authored skill shows up the same as one this UI installed — there is no separate Eldrun-tracked install-state file. **The catalog is machine state; only the install is scoped**, and `target_skills_dir` is where that one scoped decision lives: `SkillTarget::Project` names a directory (only the caller knows which project is meant), `Personal` names none and resolves against `paths::home_dir_string()` — so `~/.claude/skills/`, the destination every project *and* every uncontained session reads, is the one no caller can aim. An empty project dir is an error rather than a relative `.claude/skills` under whatever the working directory happens to be. The personal scope is also why `services::sandbox`'s `CLAUDE_UNMOUNTED` now excludes `skills`. |

| `projects/HpcPipelineWizard.tsx` | **The guided HPC/SLURM pipeline wizard** (`docs/quirky-knitting-umbrella` plan Phases B + C), launched from the project-switcher **+** menu ("HPC pipeline…"). A 6-step stepper that **composes existing flows** rather than reimplementing them: **Login** (`RemoteProjectSection` + `useRemoteSession`) → **Project** (name + local-mirror location) → **Workspace** (`lib/hpcWorkspace`: allocate or adopt an `hpc-workspace`, **then** `create_project`) → **Load data** (skippable; picks local files → `remote_upload_file` streams them to the host over the pooled SFTP) → **Run job** (edits a starter `.slurm`'s `#SBATCH` via the Phase-A splice helpers, writes it to the host, and Phase-A `submitSlurmJob`) → **Watch** (the log tab is already tailing; points at the Jobs view). The **Workspace** step is why project creation moved to the end of it: a cluster's `$HOME` is a small quota'd code filesystem, so the data belongs in a time-limited workspace on the parallel filesystem — and the integration is exactly one assignment, `remoteChosenPath = <workspace path>`, since `buildRemoteSpec` derives the host root from it and **every** transport (SFTP upload, byte-sync, git lockstep, run tabs) follows. The alternative layout (project in the browsed `$HOME` folder + the workspace symlinked in as `./data` via `hpc_ws_link`) is offered with its caveat stated: byte-sync never follows a symlink. A host with no workspace tooling skips the step's content and keeps the same single Create button. The step also offers the **home anchor** (default on): a small `~/eldrun/<project>/` with `logs/`, a `workspace` symlink and an append-only record — the only thing that still names the workspace after expiry deletes it — after which the starter script's `--output` is spliced to write job logs there. `HpcPipelineWizardHost` is mounted once in `AppShell`, driven by `stores/hpcPipeline`. Untested. |
| `projects/RemoteMachinesWindow.tsx` | **The one unified remote hub** (`docs/multi_host_remote_plan.md` §4.4): one entry per host — the **primary** first (it owns files/git/mirror; Connect/Manage only, no sync/pull/remove), then each extra "worker" machine — plus **Add a machine**. Every host's Connect/Manage opens the shared per-host `RemoteConnectDialog` (primary → `"primary"`, worker → its id), which renders on an *elevated* backdrop (`.modal-backdrop-elevated`) so the detail sits above this hub. Workers also get "Sync code now", "Pull outputs…" (size-confirmed), and the shared-fs/`sync_code` toggles. The Add-machine form opens on **"Your machines"** — the header's **global machines** (`stores/globalMachines`), offered here rather than only from the other end: a global machine is already set up and already authenticated, so retyping its address and logging into it a second time was work the dialog could do itself. A row's **Add** seeds the same confirm-shared-path panel the header menu's handoff does (`pendingDrop` → add + connect, shared-fs), so there is one add-and-connect path, not a second copy of it; **Use in the form** just fills the address/user/label for the ordinary flow (browse the folder, or sync a copy). A machine already this project's primary or worker — matched by SSH **target**, never by id, since a project host is a copy by value (`lib/machineSync`'s `sameTarget`) — is shown as "Already added" with no action. The Add-machine form's remote path can be **typed or browsed** — a **connect-then-browse** picker that runs on the SHARED login mechanism (`useRemoteBrowse` hook + `RemoteFolderBrowser` component, the exact same connect/list/mkdir machinery the new/extend-project flow uses), so there is one implementation of "log in to a host and browse it", not a worker-specific copy. Only the fields around it are this dialog's own. It connects with a transient, unsaved password (key-auth if blank) — **or**, with **"Sign in in a terminal"** (`TerminalSignInToggle`, on by default in non-headless mode), in an embedded login terminal whose ControlMaster the browse then rides via `useRemoteBrowse.openSession`, so a host that asks for a challenge code can be added at all — and browses to the folder: the existing shared folder for a shared-fs worker, or the (creatable) destination for a synced copy. Standard `modal-backdrop`+`project-dialog` chrome (worker cards = `.remote-machine-*` in themes.css). Mounted once as `RemoteMachinesDialogHost` in AppShell, driven by `stores/remoteMachines`; opened from **any of the pill's connection lamps** (`header/RemoteConnMenu` — every lamp now opens this hub, not a per-host connect), the pill's Runtime item, and the file viewer's **SSH (remote) type tag** right-click (`ProjectFilesView`, now a single "Remote machines…" item). Workers are one-way read-only experiment machines; the primary stays the project's `remote`. |
| `projects/useRemoteBrowse.ts` | **The** shared "log in to a host + browse its filesystem over SFTP" state machine — the ONE implementation of *how* a remote connect + folder browse works, so the primary machine and further (worker) machines never carry two copies. A live session is a FROZEN `(conn, password)` pair (a credential edit means `reset`+reconnect); the listing auto-refreshes on path/conn change. `connect` (ssh_connect + remember + open start dir), `openSession` (freeze a session another path already authenticated, e.g. a non-headless login terminal's ControlMaster), `enter`/`goUp`/`jump`/`mkdir`/`reset`. Used by `useRemoteSession` (new/extend-project) and `RemoteMachinesWindow` (add-worker); each keeps its own fields/steps/VPN around it. |
| `projects/RemoteFolderBrowser.tsx` | **The** remote folder-picker UI (`.remote-browser` chrome: breadcrumb, go-up, recently-used jump, inline new-folder, listing, footer), rendered by both the new/extend-project flow (`RemoteProjectSection`) and the add-worker flow (`RemoteMachinesWindow`) so the browse step is one component, not two. Owns only the new-folder input text; everything else is the caller's (fed from `useRemoteBrowse`). Exports `remoteEntryExt` (file-type icon helper). |
| `projects/TerminalSignInToggle.tsx` | **The** "Sign in in a terminal" switch — the non-headless login offered **per connect**, on both channels of both connect dialogs (`RemoteConnectDialog`, `RemoteProjectSection`), default **off**. It exists because headless can only ask what it has fields for: a host or tunnel that answers with a challenge/OTP or a second prompt can never be logged into from them, however many retries. Flipping it on swaps the password fields for the same embedded login terminal `connections_headless: false` uses. Never writes the global setting (a mode is the user's statement, not a failed handshake's), never offered on Windows (no ControlMaster to ride — the `winManual` reason), and never discards a saved credential: the Save password row renders from *both* halves of the section. The VPN modal's equivalent is a button (`stores/vpnPrompt`'s `handoffToTerminal`). See `docs/context/remote_credentials.md`. |
| `projects/CredentialPasteBar.tsx` | **The** "Type it for me" row above an embedded **login terminal** — the buttons that put a known login name, and a *saved* password, at the terminal's cursor. It exists because a terminal login and a saved credential were never the contradiction they look like: non-headless means Eldrun does not *handle* the secret (the host asks, the user answers, in a terminal they can see), not that the keychain is empty — a password saved from a headless connect, or from the header's VPN menu, was simply unreachable there and got retyped into every login. The secret never enters the frontend: a password button calls the backend `credential_paste_to_pty`, which reads the keychain and writes the bytes into the PTY itself; only non-secrets (an SSH login name, a VPN auth username the dialog already shows in a plain field) are pasted from here via the ordinary `pty_write`. Nothing is submitted — a paste is not a login, so the line stays correctable until the user presses Enter. `sshPasteEntries`/`vpnPasteEntries` build the button sets once for all three surfaces (`RemoteConnectDialog`, `RemoteProjectSection`, `RemoteMachinesWindow`); an unsaved target (or a locked keyring, which reads the same) reports "nothing saved for this login" rather than pasting an empty secret. Untested. |

| `browser/BrowserPane.tsx` | The in-app browser tab (behind the `web_browser` experimental flag). **An ordinary DOM pane, not a native view**: Plan C proved an in-pane child webview is impossible under WebKitGTK (`set_bounds` is a no-op for a GtkBox-packed child), so the tab renders **reader mode** — HTML the backend fetched and sanitized with the mail client's `ammonia` pipeline — and a real engine is a *separate hardened window* one explicit click away. Nothing about mounting reaches the network: a restored tab shows its resume card holding the persisted URL, and only `browser_restore_navigate` (default OFF) changes that. The live-page control is **hidden, not disabled**, where `browser_capabilities()` says live windows are unavailable — the capability is asked of the backend at runtime, never inferred from a platform check here. Two independent reasons put it there and the frontend deliberately cannot tell them apart: the platform (Windows in v1, whose *reader* mode works fine) and `browser_live_pages`, the **default-off, off-in-debug-too** opt-in a live page needs because a page that runs real JavaScript can reach loopback services by name and over `ws://`, neither of which is fixable from app code. Retitling from the page title is main-window-only and guarded by `autoLabelRef`, the `fileTabSync` rule: refresh the label only while it still equals the last auto-derived one. |

| `header/MachinesIndicator.tsx` | Machine-wide **global machines** (SSH hosts no project owns): the VPN indicator's pattern applied to SSH — authenticated once, with no project or path attached, then connected/monitored/reordered from the header. **Opens on click, never on hover**, and its open-sweep is rate-limited (60 s per machine, in-flight-guarded) and skips HPC-tagged rows — `ssh_probe` is a full authenticated login on each host, so a hover-opened menu logged Eldrun into the whole fleet as the pointer crossed the header. A row reads **two** maps, not one: `status` (a session this app opened) and `reachable` (the last probe), which is what lets it distinguish connected · stale (session held but no answer) · up · no answer · not checked, instead of painting a probe green. A machine reaches a project **only** through a row's "add to a project" picker (`⇥`), which lists the *open* projects and names the outcome for each: a **remote** project gains it as a `shared_fs` compute host (`stores/remoteMachines`'s `pendingDrop` → `RemoteMachinesWindow`), a **local** one is offered "Extend to remote" with it as the primary (`requestExtend` → the target's `ProjectPill`, which owns that dialog). Attaching is deliberately **not** a drag: a native HTML5 drag out of a hover-menu is unworkable under WebKitGTK (the menu closes or hangs mid-drag, and a drop that misses its target never fires, leaving the row stuck in a dimmed drag state nothing can clear) — and its target lives outside this list anyway. Rows *do* **reorder by dragging their grip**, on **pointer** events (the same choice `TabBar`/`YamlTree` made), with a keyboard ↑/↓ equivalent on the focused grip: the DOM order is frozen for the gesture and the other rows merely `transform` aside to open the landing slot, so the rects measured at pointerdown never shift under the cursor they're compared to. **Removing a machine actively disconnects it first** when it is live (`stores/globalMachines`' `remove` → `disconnect`) — dropping the row otherwise strands an SSH master, and any tmux job under it, with no handle left in the UI. Also the one entry point to **"Remote host usage…"** (`common/RemoteUsageWarningDialog` via `stores/remoteUsage`'s `open`): that report used to put itself on screen after every remote connect; it is on demand only now, and its subject is **this list** — a section per global machine in this menu's order, then the active project's own hosts not already in it (matched by SSH target, never by id) — read on demand rather than swept: opening it used to authenticate against every machine ever added, so a disconnected or HPC-tagged host now renders from cache with its own **Read now**. The **add-a-machine** form also carries **"Sign in in a terminal"** (`projects/TerminalSignInToggle`, on by default in non-headless mode): the login goes to the **root terminal** rather than an embedded PTY (a hangover from when this menu closed on mouse-out; it now opens on click and dismisses on Escape / an outside click) — and once a credential-less `ssh_connect` rides the master it left behind, the machine is `register`ed (persist without a second authentication) rather than `add`ed. Two probe commands sit behind that one list: a global machine authenticates ad-hoc (`global_machine_usage_check`, the twin of `global_machine_monitor_snapshot`), a project host rides its pooled ControlMaster (`remote_usage_check`); same script, same parser, so the sections read alike. |

| `lib/viewers/yaml.ts` | The YAML/JSON tree model + its edit ops, all pure. The tree is a **view on the text**: every edit is a surgical splice, never a re-serialization of the parsed model — the only way a config file's **comments** survive an edit, and what lets Tree and Source share one draft. **Both** YAML syntaxes are first-class: *block* (indentation) and *flow* (`{a: 1}` — i.e. **JSON**, inline or spread over lines). Which one a node is written in decides how it is edited (block → line splice, flow → span splice) and the tree keeps the author's choice, so `[a, b]` grows to `[a, b, c]` and is never quietly rewritten into block. `strict` (a `.json` file) is the only dialect knob: no plain scalars, so keys and strings are quoted. **Comments are a node's own, not scenery** — a `#` is the only place YAML documents a key, so each node reads the one behind its value *and* the run directly above it at its own indent, and `setComment` writes back wherever the author already wrote (a new one goes behind, which adds no line). The consequence is in the edits: a comment **travels with its node**, so deleting or reordering a key takes its description along rather than leaving it to re-attach itself to whichever key slid into that place. `moveNodeTo` is the one reorder op (the ↑/↓ buttons are `to = at ± 1`): a drag across five rows is **one** splice, not five swaps — every splice invalidates the offsets after it. A construct it could not rewrite without botching it (anchor, alias, merge key, plain scalar continued across lines) still *renders* but comes back `editable: false`; a line it can't classify at all fails the parse and defers to Source. |
| `lib/viewers/yamlGrid.ts` | The YAML/JSON **card grid** helpers (#yaml-grid), all pure. `hasCards` is the toggle gate (true when a collection nests another); `isContainer`/`cellKind`/`nestedLabel` classify a node so the card view never offers a control it can't honour — every EDIT is still delegated back to `yaml.ts`'s splice ops (the view-on-text bargain: comments/quoting/untouched bytes survive). Also keeps the **tabular** model (`gridModelFor`/`gridCandidates`/`hasGrid`): the flat rows × columns view of a single list/map-of-records — the card view doesn't render it, but it stays a tested, reusable "is this region a table?" helper. Tested in `src/__tests__/YamlGrid.test.ts`. |
| `lib/viewers/table.ts` | The CSV/TSV model + its edit ops, all pure. Two things it exists to say. **The separator is guessed, not known** — `.csv` never states which character separates the columns, so assuming comma from the extension is exactly what renders a `;`-delimited export as one tall column; `sniffDelimiter` scores each candidate by parsing a sample *with* it (a comma inside a quoted field cannot fool the `;` reading) and asking how rectangular the result is, rejecting any character that never splits a row however consistently it fails to appear. And **the table is a view on the text**: `parseTable` hands back each cell's source span, so `replaceCell`/`insertRowAfter`/`deleteRow` are surgical splices — the only way editing one cell leaves every other field's quoting, the file's line endings and its delimiter byte-for-byte alone. Same bargain `yaml.ts` strikes for comments. |
| `lib/viewers/gif.ts` | The GIF decoder, all pure — takes a `Uint8Array`, never touches the fs (WebKitGTK has no `ImageDecoder` API, so frame control means decoding LZW + interlace + disposal 0–3 ourselves; GIF89a is frozen, so no maintenance tail). Two ideas: **every frame composites to a full-canvas RGBA buffer** (GIF has no keyframes — frame N is a patch on N−1's state, so upfront full frames are what make scrubbing O(1); memory is bounded by `maxPixelBytes`, beyond which the result says `truncated`), and **delays are stored as authored, played by convention** (`effectiveDelayMs`: <20ms means "browser default" = 100ms — files were authored against that clamp). Disposal 2 clears to *transparent*, not the spec's background color, because that is what every browser does. Corruption after ≥1 good frame returns the clean prefix + `truncated`; before it, throws. |

| `lib/gpu.ts` | The GPU-memory arithmetic shared by its three surfaces (header row, system monitor, local-model menu), pure; sampling is the backend's `gpustat`. The one idea: **GPU memory is the two pools summed** — the dedicated VRAM carve-out *and* the shared pool mapped from system RAM — because on an APU the carve-out is only the framebuffer (~86% full forever, meaningless) while a model actually lands in the shared half; on a discrete card the shared half is 0 and the sum is plain VRAM. Hence `gpuTone` tones by **ratio**: the old row's absolute 1 GB/2 GB thresholds suited a figure counting only Ollama's models and would peg a device-wide one at "hot" permanently. Also home to the **sensor** formatters (`formatTempC`/`formatWatts`/`formatMhz`/`formatFan`/`gpuLinkLabel`) and the `GpuProc` type: each formatter returns `null` for an unreported reading so the UI omits it rather than print a fake zero, and `gpuAdapterTooltip` appends only the sensors the driver actually gave. The system-monitor pane renders these as a per-adapter GPU card (VRAM + Util meters, sensor strip) plus a once-only per-process GPU-memory list (locally from `gpu_process_snapshot`; for a remote source, from the host-sampled `SystemSnapshot.gpu_procs` in the same poll). |

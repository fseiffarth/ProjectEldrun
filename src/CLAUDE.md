Also **pre-checks whether the site is already a project** (#152) as the folder/host path is picked, via `check_project_site` — the *same* resolver the backend refuses with, so the warning and the refusal cannot disagree. It is advisory (the list can move under it) and the write-side gate is the real one, but it is what stops a clone or fork from downloading a whole repository into a destination that is about to be rejected; a missing command resolves to "no conflict" rather than blocking a dialog against an older backend. The notice names the colliding project and offers to **open it**, because a dead-end error would leave the user to go find it. The site it checks mirrors the backend's: the host path when remote, else the folder the project ends up in — which for a *copy* import is the destination, not the source it copies from. |

| `projects/HpcPipelineWizard.tsx` | **The guided HPC/SLURM pipeline wizard** (`docs/quirky-knitting-umbrella` plan Phases B + C), launched from the project-switcher **+** menu ("HPC pipeline…"). A 6-step stepper that **composes existing flows** rather than reimplementing them: **Login** (`RemoteProjectSection` + `useRemoteSession`) → **Project** (name + local-mirror location) → **Workspace** (`lib/hpcWorkspace`: allocate or adopt an `hpc-workspace`, **then** `create_project`) → **Load data** (skippable; picks local files → `remote_upload_file` streams them to the host over the pooled SFTP) → **Run job** (edits a starter `.slurm`'s `#SBATCH` via the Phase-A splice helpers, writes it to the host, and Phase-A `submitSlurmJob`) → **Watch** (the log tab is already tailing; points at the Jobs view). The **Workspace** step is why project creation moved to the end of it: a cluster's `$HOME` is a small quota'd code filesystem, so the data belongs in a time-limited workspace on the parallel filesystem — and the integration is exactly one assignment, `remoteChosenPath = <workspace path>`, since `buildRemoteSpec` derives the host root from it and **every** transport (SFTP upload, byte-sync, git lockstep, run tabs) follows. The alternative layout (project in the browsed `$HOME` folder + the workspace symlinked in as `./data` via `hpc_ws_link`) is offered with its caveat stated: byte-sync never follows a symlink. A host with no workspace tooling skips the step's content and keeps the same single Create button. The step also offers the **home anchor** (default on): a small `~/eldrun/<project>/` with `logs/`, a `workspace` symlink and an append-only record — the only thing that still names the workspace after expiry deletes it — after which the starter script's `--output` is spliced to write job logs there. `HpcPipelineWizardHost` is mounted once in `AppShell`, driven by `stores/hpcPipeline`. Untested. |
| `projects/RemoteMachinesWindow.tsx` | **The one unified remote hub** (`docs/multi_host_remote_plan.md` §4.4): one entry per host — the **primary** first (it owns files/git/mirror; Connect/Manage only, no sync/pull/remove), then each extra "worker" machine — plus **Add a machine**. Every host's Connect/Manage opens the shared per-host `RemoteConnectDialog` (primary → `"primary"`, worker → its id), which renders on an *elevated* backdrop (`.modal-backdrop-elevated`) so the detail sits above this hub. Workers also get "Sync code now", "Pull outputs…" (size-confirmed), and the shared-fs/`sync_code` toggles. The Add-machine form opens on **"Your machines"** — the header's **global machines** (`stores/globalMachines`), offered here rather than only from the other end: a global machine is already set up and already authenticated, so retyping its address and logging into it a second time was work the dialog could do itself. A row's **Add** seeds the same confirm-shared-path panel the header menu's handoff does (`pendingDrop` → add + connect, shared-fs), so there is one add-and-connect path, not a second copy of it; **Use in the form** just fills the address/user/label for the ordinary flow (browse the folder, or sync a copy). A machine already this project's primary or worker — matched by SSH **target**, never by id, since a project host is a copy by value (`lib/machineSync`'s `sameTarget`) — is shown as "Already added" with no action. The Add-machine form's remote path can be **typed or browsed** — a **connect-then-browse** picker that runs on the SHARED login mechanism (`useRemoteBrowse` hook + `RemoteFolderBrowser` component, the exact same connect/list/mkdir machinery the new/extend-project flow uses), so there is one implementation of "log in to a host and browse it", not a worker-specific copy. Only the fields around it are this dialog's own. It connects with a transient, unsaved password (key-auth if blank) — **or**, with **"Sign in in a terminal"** (`TerminalSignInToggle`, on by default in non-headless mode), in an embedded login terminal whose ControlMaster the browse then rides via `useRemoteBrowse.openSession`, so a host that asks for a challenge code can be added at all — and browses to the folder: the existing shared folder for a shared-fs worker, or the (creatable) destination for a synced copy. Standard `modal-backdrop`+`project-dialog` chrome (worker cards = `.remote-machine-*` in themes.css). Mounted once as `RemoteMachinesDialogHost` in AppShell, driven by `stores/remoteMachines`; opened from **any of the pill's connection lamps** (`header/RemoteConnMenu` — every lamp now opens this hub, not a per-host connect), the pill's Runtime item, and the file viewer's **SSH (remote) type tag** right-click (`ProjectFilesView`, now a single "Remote machines…" item). Workers are one-way read-only experiment machines; the primary stays the project's `remote`. |
| `projects/useRemoteBrowse.ts` | **The** shared "log in to a host + browse its filesystem over SFTP" state machine — the ONE implementation of *how* a remote connect + folder browse works, so the primary machine and further (worker) machines never carry two copies. A live session is a FROZEN `(conn, password)` pair (a credential edit means `reset`+reconnect); the listing auto-refreshes on path/conn change. `connect` (ssh_connect + remember + open start dir), `openSession` (freeze a session another path already authenticated, e.g. a non-headless login terminal's ControlMaster), `enter`/`goUp`/`jump`/`mkdir`/`reset`. Used by `useRemoteSession` (new/extend-project) and `RemoteMachinesWindow` (add-worker); each keeps its own fields/steps/VPN around it. |
| `projects/RemoteFolderBrowser.tsx` | **The** remote folder-picker UI (`.remote-browser` chrome: breadcrumb, go-up, recently-used jump, inline new-folder, listing, footer), rendered by both the new/extend-project flow (`RemoteProjectSection`) and the add-worker flow (`RemoteMachinesWindow`) so the browse step is one component, not two. | `projects/TerminalSignInToggle.tsx` | **The** "Sign in in a terminal" switch — the non-headless login offered **per connect**, on both channels of both connect dialogs (`RemoteConnectDialog`, `RemoteProjectSection`), default **off**. It exists because headless can only ask what it has fields for: a host or tunnel that answers with a challenge/OTP or a second prompt can never be logged into from them, however many retries. Flipping it on swaps the password fields for the same embedded login terminal `connections_headless: false` uses. Never writes the global setting (a mode is the user's statement, not a failed handshake's), never offered on Windows (no ControlMaster to ride — the `winManual` reason), and never discards a saved credential: the Save password row renders from *both* halves of the section. | `projects/CredentialPasteBar.tsx` | **The** "Type it for me" row above an embedded **login terminal** — the buttons that put a known login name, and a *saved* password, at the terminal's cursor. It exists because a terminal login and a saved credential were never the contradiction they look like: non-headless means Eldrun does not *handle* the secret (the host asks, the user answers, in a terminal they can see), not that the keychain is empty — a password saved from a headless connect, or from the header's VPN menu, was simply unreachable there and got retyped into every login. Nothing is submitted — a paste is not a login, so the line stays correctable until the user presses Enter. `sshPasteEntries`/`vpnPasteEntries` build the button sets once for all three surfaces (`RemoteConnectDialog`, `RemoteProjectSection`, `RemoteMachinesWindow`); an unsaved target (or a locked keyring, which reads the same) reports "nothing saved for this login" rather than pasting an empty secret. Untested. |

| `todo/TodoBoard.tsx` | The Trello-shaped board **and the owner of the card drag**. Three rules, all forced by the engines: the commit is bound through `bindDragRelease` **synchronously inside pointerdown** (WebKitGTK never delivers the terminal pointerup to listeners added mid-gesture — `TabBar` documents the same trap), pointer capture goes on `documentElement` and never on the card (which unmounts mid-gesture as the placeholder re-renders), and because `pointercancel` **commits** on Linux the commit must be safe under a target the user never chose — no column under the pointer means the card simply stays put, never a default column and never a delete. A drag is ONE backend write (`todo_move_tasks`), whatever it moved. |
| `todo/TodoColumn.tsx` / `todo/TodoCard.tsx` | A column (header, cards, composer) and a card (checkbox, inline-editable title, due/priority/tag chips, checklist, project chip, mail link). The composer's **Enter creates and stays open** — adding five cards in a row is what a board is for. Every inner control stops the pointer, or clicking a checkbox seeds a drag; every text input stops its own Escape, or renaming a card closes the whole overlay (`stopPropagation` does not stop sibling listeners on `window`). The card's **checklist is inline and editable on the board** — the progress bar is its disclosure control, the head's `＋` opens it on a card that has none yet, and a step is ticked, added or dropped without opening the dialog, because breaking a card into steps is something you do *while* looking at the column you were reasoning about. It writes on **every edit** (a board has no Save, so a staged checklist would be a draft the user cannot see is unsaved) and reads the card back out of the store rather than off its props first, or a second Enter one frame after the first would drop the step the first one added. Renaming a step is still the dialog's — there is no room for a text field per row here. The ops themselves are `lib/todoBoard`'s, shared with the dialog. |

| `mail/MailPane.tsx` | The embedded mail client (behind the `mail_client` experimental flag): folder rail / header list / message view. Global store, no PTY, no project props — the same shape as `CalendarPane`. **It has exactly one host, `MailOverlay`** — there is no mail *tab* any more. There was one, and it was redundant from the start: the store is global, so the tab showed the same mailbox from every scope while still belonging to a project you then switch away from. The rail's top section is **Priority** — the **Important** and **Urgent** lists, above and outside Accounts because that is what they are: every account's marked mail in one place, and nesting them under an account would say the opposite. Both render even when empty, since an empty list is where the feature is discovered. |
| `mail/MailOverlay.tsx` | **The** mail surface (`mail_client`): the header ✉ button's overlay, mounted once in `AppShell` as `MailOverlayHost`. It renders `MailPane` floated over the window instead of tiled into a scope — which, since the mail tab was retired, is the only way mail is on screen at all; all this adds is a size and an Escape/backdrop close. **One gate, not two**: `mail_global_app` used to sit under `mail_client` to decide whether the header carried a button *as well as* the tab, and with the tab gone that second switch could only ever mean "mail on, and unreachable" — so it is gone from `Settings` on both sides (an old `settings.json` still holding the key is fine; serde ignores fields the struct no longer declares). It rides the app's canonical dialog chrome (`.project-dialog.dialog-framed` + `.settings-title-row` + `.dialog-close-btn`), applied exactly as `GlobalMachineMonitorDialog` applies it to the system-monitor pane — same shape of thing, a whole pane in a dialog, sized by its own rule with a body that clips rather than scrolls. At the shell rather than in the header because it covers the window and must survive a project switch. |
| `mail/MailList.tsx` | The header list. Enforces two threat-model rules in the rendering itself: the **addr-spec is always shown** beside a sender's display name (an attacker-chosen name must never stand in for identity), and every mail-derived string is a plain text node. The list is a real **column grid** — star · read-dot · clip · sender · size · date — whose template (`--mail-cols`) is declared once on `.mail-list` and used by both the header row and every message row; that shared declaration is what makes them line up, and every column but the sender is a **fixed** width because each row is its own grid container, so `auto` tracks would size per row and turn the columns into a staircase. The clip is a column with an empty cell rather than a marker in front of the subject (a marker that shifts the subject when absent is not a column), and the size is printed on every row rather than only under its own sort, so selecting that sort does not move the other columns sideways. **The sort controls are the column headers** (star / clip / size / date — click to sort, click the sorted one to reverse, arrow only on the sorted column), which is the one thing the list does *not* implement: it is handed one page, so it hands the pair back through `onSort` and the ordering happens in SQLite over the whole folder — the biggest message in a mailbox is rarely among the newest hundred. The **sender** header is deliberately inert: `from` is stored as JSON, so ordering by it would sort by `{"name":…`, and a header that sorts wrongly is worse than one that does not sort. Also the **right-click menu** that files a message into **Important** or **Urgent** — the only way in, because two marks plus an unmark is three glyphs the rows nobody is filing would pay for. Portaled to `<body>` at the cursor (the pattern `ProjectFilesView`'s type-tag menu uses): this list scrolls and clips, so an in-flow menu on the last visible row would open inside the overflow. Right-clicking also *selects* the row — the menu naming the wrong mail while the message pane shows another is how the wrong thing gets filed — and the menu quotes the subject (stripped of format controls, like every other place a subject is printed) plus a footnote saying what "move" does **not** do: nothing leaves the folder it is in. A row carries its mark as `!`/`!!` wherever it appears, not just in the priority list, because that is the only place the user can see the filing worked. |
| `mail/MailMessageView.tsx` | The message pane. The body renders in `<iframe sandbox="">` with **neither `allow-scripts` nor `allow-same-origin`** (together they are a total sandbox escape) plus its own `<meta>` CSP — an inline meta rather than the `csp=` attribute, which WebKitGTK does not implement. The sanitized HTML carries **no `href`**: links are `data-lid` markers resolved against `MailBody.links` and opened only after a confirm that names the real host. Remote content is blocked with **no control offered to unblock it** — the backend has no image proxy yet, so a "Load remote content" button would clear the banner, report success and fetch nothing; blocked and honest beats a control that lies. Attachments Save via `mail_attachment_save` (the backend raises the OS dialog) or preview in-pane; there is deliberately no "open with the system app". Also hosts `MailCryptoPanel` — end-to-end signatures/encryption, **beside** the sender checks rather than merged with them, because they answer different questions (what your server concluded about the delivering hop, vs. what the sender did before the message left their machine) and a message can pass one while failing the other. The chrome rule is the backend's: the component renders `info.state` and `mailCryptoTone` is the single mapping to appearance, so `known` — a valid signature from a key nobody checked — is *neutral*, never green. Also hosts `MailAuthPanel` — the **sender checks** (SPF/DKIM/DMARC) read out of `Authentication-Results`, shown only when the account named a trusted `authserv-id` *and* the topmost header carried it; a configured account that got someone else's header gets a named warning, and a message with no header at all renders nothing, because absence is not failure. |
| `mail/MailEncryptionDialog.tsx` | **The local store's encryption** (`docs/context/mail_encryption.md`), one dialog with three faces chosen by `MailEncryptionState` rather than by a prop, so it cannot disagree with the backend about what is going on: **unlock** (a passphrase store currently showing its memory-only stand-in), **offer** (never asked — and for an install that already holds mail, "Delete and download again" is offered *beside* migration rather than buried, because a migration cannot reliably erase what it replaces on an SSD), and **status**. What the copy must not overstate is the whole design: FDE already covers the stolen laptop, so what this adds is backups, copies, cloud-synced folders and multi-user machines — and nothing at all against a live process. A security feature that oversells itself buys behaviour changes it did not earn. |
| `mail/MailKeysDialog.tsx` | **The OpenPGP keyring.** Built around the fingerprint, because with no certificate authority the fingerprint *is* the trust model: shown in full, grouped in fours, monospace, wrapping, **never truncated** — 40 run-together hex characters do not get compared, they get glanced at, and an abbreviated one is worse than none because it still looks checked. The "I checked this with its owner" box is the only path to positive chrome anywhere in the feature, and it is reversible, because a claim the user made can turn out to be wrong. Export is public-only and says so: "export my key", typed by somebody who means the public half, is the standard way a private key ends up in an email. |

| `lib/viewers/yaml.ts` | The YAML/JSON tree model + its edit ops, all pure. The tree is a **view on the text**: every edit is a surgical splice, never a re-serialization of the parsed model — the only way a config file's **comments** survive an edit, and what lets Tree and Source share one draft. **Both** YAML syntaxes are first-class: *block* (indentation) and *flow* (`{a: 1}` — i.e. **JSON**, inline or spread over lines). Which one a node is written in decides how it is edited (block → line splice, flow → span splice) and the tree keeps the author's choice, so `[a, b]` grows to `[a, b, c]` and is never quietly rewritten into block. `strict` (a `.json` file) is the only dialect knob: no plain scalars, so keys and strings are quoted. **Comments are a node's own, not scenery** — a `#` is the only place YAML documents a key, so each node reads the one behind its value *and* the run directly above it at its own indent, and `setComment` writes back wherever the author already wrote (a new one goes behind, which adds no line). The consequence is in the edits: a comment **travels with its node**, so deleting or reordering a key takes its description along rather than leaving it to re-attach itself to whichever key slid into that place. `moveNodeTo` is the one reorder op (the ↑/↓ buttons are `to = at ± 1`): a drag across five rows is **one** splice, not five swaps — every splice invalidates the offsets after it. A construct it could not rewrite without botching it (anchor, alias, merge key, plain scalar continued across lines) still *renders* but comes back `editable: false`; a line it can't classify at all fails the parse and defers to Source. |

| `lib/viewers/table.ts` | The CSV/TSV model + its edit ops, all pure. Two things it exists to say. **The separator is guessed, not known** — `.csv` never states which character separates the columns, so assuming comma from the extension is exactly what renders a `;`-delimited export as one tall column; `sniffDelimiter` scores each candidate by parsing a sample *with* it (a comma inside a quoted field cannot fool the `;` reading) and asking how rectangular the result is, rejecting any character that never splits a row however consistently it fails to appear. And **the table is a view on the text**: `parseTable` hands back each cell's source span, so `replaceCell`/`insertRowAfter`/`deleteRow` are surgical splices — the only way editing one cell leaves every other field's quoting, the file's line endings and its delimiter byte-for-byte alone. Same bargain `yaml.ts` strikes for comments. |
| `lib/viewers/gif.ts` | The GIF decoder, all pure — takes a `Uint8Array`, never touches the fs (WebKitGTK has no `ImageDecoder` API, so frame control means decoding LZW + interlace + disposal 0–3 ourselves; GIF89a is frozen, so no maintenance tail). Two ideas: **every frame composites to a full-canvas RGBA buffer** (GIF has no keyframes — frame N is a patch on N−1's state, so upfront full frames are what make scrubbing O(1); memory is bounded by `maxPixelBytes`, beyond which the result says `truncated`), and **delays are stored as authored, played by convention** (`effectiveDelayMs`: <20ms means "browser default" = 100ms — files were authored against that clamp).
